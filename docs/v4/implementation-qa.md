# QA indépendante V4 — implémentation locale

Statut : 50 tests indépendants du code V4 et 4 parcours Chromium exécutés et réussis, 0 échec, 0 ignoré. Commande : `node --test tests/v4*.test.mjs`. Ces tests portent sur les vrais modules du moteur et de l'API V4, et non sur le modèle de contrat d'architecture.

## Preuves locales

- Moteur : dix réponses initiales d'entraînement puis cinq de mini-test exigées avant clôture; correction serveur; valeurs de score/XP client ignorées; première réponse conservée et clôture idempotente.
- Points : 10 XP par réponse correcte et bonus 50 XP à partir de 4/5; six essais donnant les gains complets; arrêt après six clôtures ou trois chapitres distincts réussis par matière/date Brussels.
- API : contrôle propriétaire/rôle parent/lien; refus anonyme et absence de fallback Memory dans le handler déployable sans configuration; mode qualité refusé en production sans stockage QA explicitement distinct; stockage QA distinct configuré testé sans modification du compte réel.
- Concurrence du MemoryStore réel : vingt créations parallèles produisent une seule séance active; vingt-cinq clôtures parallèles produisent un seul crédit, historique, journal et compteur. Ce résultat ne prouve pas la concurrence Firestore.
- Isolation qualité : namespace distinct, aucune notification, aucun état élève modifié; mission normale suivante créditée.
- Mini-test : DTO sans théorie/corrigés futurs ni réponses corrigées; endpoint d'aide refusé même avec phase client falsifiée; aide préparée explicitement sans IA en absence du fournisseur.
- Contenus : 21 chapitres anglais et 20 maths; cinq familles dans chaque phase; six séries renouvelées par générateur, questions et choix distincts. Oracle arithmétique indépendant et contrôle mathématique des QCM de divisibilité. Contractions et apostrophes testées. Les critères pédagogiques s'appuient aussi sur les revues des professeurs.
- HTTP local : 41 séances complètes via la vraie API V4, projet mémoire fictif et authentification injectée explicitement. Chaque séance qualité atteint 100 % avec 0 XP; la mission anglaise normale suivante crédite 200 XP et apparaît dans le dashboard. Le stockage est mémoire, sans preuve cloud.
- Migration : véritable format V3 `sessions`, solde conservé sans recalcul, origine conservée, progression remappée par identifiant stable malgré ordre maths changé, quotas/maîtrises issus des seules séances normales documentées, demandes de récompenses historiques exposées sans rejouer les dépenses, dates invalides refusées et répétition idempotente.
- Inactivité : trois jours calendaires complets sans débit, puis 5/10/15/20 % sur une base figée; solde jamais négatif, aucune dette différée du même palier; dates Brussels et DST.
- Migration Firestore : adaptateur exercé avec faux Firestore transactionnel, archivage Unicode privé par blocs inférieurs à 64 KiB et checksum SHA256; reconstruction et réapplication sans double crédit; rejets avant toute écriture au-delà des budgets documents/transactions. Défaut de volume total trouvé par QA puis corrigé : budget conservateur de 5 MiB pour les écritures et marge index. Ces tests ne prouvent pas Firestore réel.
- Notifications : leases transactionnels empêchant les appels fournisseurs concurrents, corps figé entre reprises, destinataire révoqué jamais recontacté, événement ambigu au-delà de 23 h soumis à revue, deux envois maximum par passage; vrai dispatcher testé avec fournisseur injecté fictif; échec puis reprise, clé d'idempotence, aucun retrait de crédit en cas d'échec. Aucun e-mail réel envoyé ou reçu dans ces tests.
- Publication : sortie `dist` limitée aux cinq assets navigateur; aucun moteur, générateur ou corrigé privé publié; serveur HTTP local refuse les chemins privés.

## Défauts trouvés et corrigés durant QA

Mauvaise enveloppe API interprétée par le client; options vides des questions texte traitées comme QCM; capacité anglaise insuffisante pour six essais renouvelés; migration ignorant initialement `sessions` V3 et progression; dates invalides acceptées; rôle enfant pouvant accéder à un lien parent résiduel; perte visuelle des récompenses historiques; risque de déploiement d'un environnement non reconnu avec identifiants de production; documents privés pouvant être publiés depuis la racine V4. Les tests correspondants ont été rejoués après correction.

## Limites et conditions de production

Les quatre parcours navigateur ont été exécutés avec `V4_CHROMIUM_EXECUTABLE=/workspace/scratch/d6011c7be4e2/browser-runtime/extracted/chromium node --test tests/v4-e2e.spec.mjs` : qualité → normal → 200 XP et historique après recharge; maths avec aide préparée explicitement sans IA, reprise à la bonne question, aide/théorie absentes pendant le test, score de 0 % puis nouvelle série dans la même notion, avis enregistré; trois notions anglaises réussies bloquant seulement l’anglais; service non configuré refusant tout tableau de bord fictif; demande élève, refus/remboursement parent, accès Snap conditionné à l’attestation d’âge. Les acteurs et le stockage sont des fixtures locales explicites, pas Firebase. Question libre d’aide effectivement envoyée au serveur; bouton audio de réponse présent; dictée indisponible simulée avec repli écrit; ces trois contrôles absents au mini-test. Parcours de 20/21 notions visible. La capture a été régénérée après ces changements. Capture iPad inspectée : `test-results/v4-ipad-home.png` (834 × 1194), cartes et contrôles lisibles, quota anglais désactivé et mathématiques disponible. La salutation utilise désormais du texte simple, sans glyphe manquant.

Firebase Auth réel, transactions Firestore multiappareil, sauvegarde/restauration de données réelles, migration réelle, appel IA avec clé réelle, fournisseur e-mail et réception des rapports restent non éprouvés. Le déclenchement réel du scheduler Netlify et l’index notifications.status restent à tester; le worker limite sa page à vingt éléments sans ordre de disponibilité, pouvant retarder des événements récents en présence d’un backlog bloqué. Cette limite est documentée pour le petit déploiement et nécessite pagination/ordre avant augmentation du volume. Les identifiants et la configuration externe sont nécessaires. Le handler refuse l'accès plutôt que de prétendre enregistrer dans le cloud si sa configuration manque. Les tests de fournisseur utilisent des injections explicites, pas des services réels.

**Verdict : contrôles locaux exécutés réussis; aucune autorisation QA de production avant les preuves navigateur et d'intégration préproduction.**
